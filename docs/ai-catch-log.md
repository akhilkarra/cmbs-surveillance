# AI catch log

Each entry records a case where an AI tool produced something wrong or incomplete, and how it was caught. In finance a silently wrong number is worse than a crash.

| Date | Tool / step | What the AI said | What was actually true | How it was caught | Guardrail added |
|---|---|---|---|---|---|
| 2026-10-24 | Name-matching filter for CMBS lines in the N-PORT holdings | Flagged "Flagstar Bank NA" as CMBS; missed PRM7 2025-PRM7. | A filter on deal names gives both false positives and false negatives, because N-PORT has no CMBS/RMBS flag (both fall under `ABS-MBS`). | Manual review of the matched list. | Classify by CUSIP / deal-shelf lookup and add a manual review step; report the heuristic's coverage as approximate. |
| 2026-10-24 | Holdings classifier (agent), rule based on deal-name suffix | Labeled PNW 2026-ARTE and CSMC 2017-PFHP as RMBS. | Both are commercial SASB deals. | Spot-checked the rule output against deal research. | Rule table plus a manual override file; the suffix rule is flagged as the main risk when classifying older periods. |
| 2026-10-24 | Holdings classifier, full history (26 periods) | Counted Hertz Vehicle Financing, Exeter/GLS/Carvana auto receivables, Sierra Timeshare, Upstart, Navient and GSAMP as CMBS. That inflated the 2022-04 CMBS sleeve to 37.7% of NAV. | Older N-PORTs file some consumer ABS under `ABS-MBS`. Their `2021-1A`-style series ids then matched the loose SASB-ticker rule (L4). The true figure is 22.3%. | Reviewed the deals each rule caught in the first full-history run, since a rule tested on one period hadn't been tested on the others. | Added an exclusion rule (L2d, plus L2c for GSAMP) that runs before L4, and a regression check that no consumer-ABS keywords remain in the CMBS bucket. |
| 2026-10-24 | WebFetch summary of the Claude Code hooks docs (agent-dev research) | "`stop_hook_active` is not documented." | It is documented. The page is 281,770 characters and WebFetch read only the first 100,000. **This is the same failure as entry 1, which happened again.** | The agent downloaded the full page with curl and searched it. | Make it standing practice: for any "absent/not documented" claim, fetch the full source and search it. Consider a hook that flags WebFetch results that note truncation. |
| 2026-10-24 | Data-source research agent | Called JPMCC 2017-FL11 publicly registered. | No 10-D or ABS-EE exists under its name, so it's likely a 144A private placement. | A second agent cross-checked with EDGAR full-text search. | Independent cross-check between agents on any "is public" claim. |
| 2026-10-24 | Market primer agent | Used the brief's player list as given (Wells as servicer and trustee, Arena, DBRS Morningstar). | Wells's servicing went to Trimont (2025) and its trust business to Computershare (2021). Arena is now CCaventus; DBRS Morningstar is now Morningstar DBRS. | The agent re-verified each name against current sources instead of trusting the prompt. | Briefs ask agents to re-verify named entities; prompt content isn't treated as fact. |
| 2026-10-27 | Stack research (`research/20-stack.md` §4), planned CI action versions | CI should use `astral-sh/setup-uv@v10`. | The newest major tag of setup-uv is v7; v10 does not exist. | Listed the action's tags with `git ls-remote` before writing the workflow. | Check every pinned action or hook version against the source repository's tags before committing it. |
| 2026-10-27 | Accepted-feature CI check (agent-written) | Required an `Approved-by:` trailer on any commit touching `features/accepted/`. | The bootstrap commit that only added the empty manifest failed CI. Manifest-only changes are already caught by the hash check, so the trailer rule only needs to cover `.feature` files. | CI failed on push; reproduced locally with the same commit range. | The trailer rule now targets accepted `.feature` files; tamper tests rerun for missing trailer, trailer present, and post-acceptance edit. |
| 2026-10-28 | CI setup (agent-written) | The project declared `requires-python >= 3.13` with no pinned version, and CI was assumed to run 3.13. | The runner's uv picked Python 3.15. `minify-html` (via behavex) has no 3.15 wheel, and building it from source fails because PyO3 supports Python only up to 3.14. Local and container runs passed because they all used 3.13. | Read the failed step's log with `gh run view --log-failed`, then reproduced with `uv sync --locked --python 3.15`. | `.python-version` pins 3.13 for local runs, CI and containers alike. |
| 2026-10-28 | Diagnosing slow mutation runs and an unresponsive Docker (agent) | The VM was overloaded by parallel test databases, and mutants hung on database locks; OrbStack was restarted, and a commit message called lock waits the cause of a 53-minute run. | The Mac was asleep from 23:21 to 07:08 apart from brief maintenance wakes, which freezes Docker and every process. With the machine awake, the same full run took 75 seconds. Lock timeouts on test connections are still worth keeping, but they were not the main cause. | The user asked whether sleep was the reason; the power log (`pmset -g log`) showed the sleep window. | Check `pmset -g log` before diagnosing a stall, keep the machine awake during long work, and state a cause only when the evidence rules out the alternatives. |
| 2026-10-28 | Loan-tape mutation shards timing out in CI (agent and lead) | The agent blamed one endless-loop mutant, then a local Docker outage, and suspected database waits under some mutants. | Postgres logged no lock or statement timeouts. A stack dump of a hung mutant showed it waiting in a Polars `collect()` inside the Pandera contract: mutmut forked each mutant from a process whose Polars thread pool was already running, so nearly every loan-tape mutant hung whatever it changed. The "outage" was the Mac sleeping again. | Reproduced one timed-out mutant under plain pytest (killed in 4 s) and under mutmut (timeout, under 4 s of CPU), then dumped the hung child's stacks with faulthandler on SIGUSR1. | When mutants time out en masse, compare the plain-pytest run with mutmut's and dump the hung child's stack before guessing; run mutmut with fork-server isolation. |
| 2026-10-29 | Lead's merge command for PR 28 | A merge script and a branch cleanup were chained with `;` in one shell command, so the cleanup ran although the script had stopped with "#28 is not clean". | The PR's branch was deleted locally and on GitHub while the PR was unmerged, which closed it. Nothing was lost: the commit was still in the local object store. | Read the script's output: it said STOP, yet the branch list showed the branch gone. Recreated the branch from its last commit, pushed it and reopened the PR. | Cleanup happens inside the merge script, only after it confirms the PR's state is MERGED. Never chain destructive steps after a step whose failure a pipe or `;` hides. Never edit a script while a run of it is in flight: bash reads the file as it executes. |
| 2026-10-31 | Lead's merge of the Q90/Q91 docs PR | Assumed the new PR would be number 43, the next after the last merged one, and passed that number to the merge script in the same command that opened the PR. | Dependabot had opened #43 and #44 in the meantime; the docs PR was #45. The script merged Dependabot's jsdom patch bump (#43) under the docs PR's subject. Its CI was green and the bump was due to merge anyway, but it went in without the local check, and main's history carries the wrong title. | Read the script's output: `gh pr create` printed #45 while the script reported merging #43 and deleting a Dependabot branch. Ran the web tests, coverage and Biome on main afterwards: all pass. | The merge script now takes the PR's head branch as well and refuses when the PR comes from another branch or the subject's `(#N)` differs; the PR number is read from `gh pr create`'s output, never predicted. |
